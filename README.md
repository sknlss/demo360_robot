# Мини-воронка регистраций в Telegram + дашборд в мини-аппе

Бот на aiogram 3: `/start` → приветствие → запрос телефона → два напоминания по расписанию
(через 10 секунд и через минуту), пока номера нет. Ответ человека (номер или отказ) обрывает расписание и ведёт на свой шаг.
Тексты, шаги и тайминги — в `funnels.yml`.
Дашборд — одна HTML-страница (мини-апп) с двумя разделами. «Воронки»: список воронок из конфига; внутри воронки —
сводка («запустил → получил запрос номера → дал телефон»), кнопка «Подробнее» (уровни со списками людей, статистика
по шагам, последние события) и структура воронки шагами с кнопкой «Редактировать» (только для администраторов): конструктор шагов, который правит тот же `funnels.yml`.
«Пользователи»: все пользователи из базы без фильтров. Переходы между экранами идут в памяти страницы, адрес не меняется
(в нём подпись Telegram).

Один процесс: опрос Telegram, петля отправки отложенных сообщений и веб-дашборд работают вместе.
Стек: Python 3.12, aiogram 3, aiohttp, PyYAML, SQLite (файл).

## Запуск

Нужен токен бота от [@BotFather](https://t.me/BotFather).

```bash
cp .env.example .env     # впишите BOT_TOKEN; для просмотра в обычном браузере поставьте DASHBOARD_AUTH_DISABLED=1
```

**Напрямую через Python:**

```bash
python3.12 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
python -m app
```

**Контейнером:**

```bash
mkdir -p data
docker compose up -d --build
```

`compose.yml` порт не публикует. Чтобы открыть дашборд снаружи, создайте `compose.override.yml`:

```yaml
services:
  bot:
    ports: ["127.0.0.1:8080:8080"]
```

Дашборд: <http://127.0.0.1:8080/>. Без `DASHBOARD_AUTH_DISABLED=1` данные отдаются только внутри Telegram
(см. «Доступ»). Для просмотра в обычном браузере поставьте `DASHBOARD_AUTH_DISABLED=1` — тогда телефоны видны целиком. Чтобы открыть дашборд кнопкой из бота, задайте `MINIAPP_URL` (https-адрес) и
отправьте боту `/dashboard`; или привяжите адрес к мини-аппу в @BotFather.

**Публикация по пути (`https://example.com/tg-demo/`).** Страница просит данные по относительным путям
(`api/funnels`, `api/overview?funnel=…`, `api/users`, `api/photo/<id>`), без ведущей `/`, поэтому работает и в корне домена, и под
префиксом. Условие: адрес страницы заканчивается на `/` — без неё браузер отсчитает путь от родителя и вернётся 404.
`MINIAPP_URL` без `/` на конце дополняется сам. Прокси должен срезать префикс (`/tg-demo/api/funnels` → `/api/funnels`)
и передавать заголовок `X-Init-Data`. Проверка — `tests/test_base_path.py`.

Второй процесс с той же папкой данных не стартует и пишет, кто держит замок.

### Переменные окружения

Все описаны в [`.env.example`](.env.example): `BOT_TOKEN`, `ADMIN_IDS`, `DASHBOARD_AUTH_DISABLED`, `MINIAPP_URL`,
`WEB_HOST`, `WEB_PORT`, `DB_PATH`, `PHOTO_CACHE_DIR`, `CONFIG_PATH`, `INIT_DATA_MAX_AGE`, `TELEGRAM_API_BASE`, `LOG_LEVEL`.

**Приоритет:** переменная окружения сильнее `.env`. Файл лишь добавляет то, чего в окружении нет, и ничего не
перезаписывает; поэтому в Docker настройки из `compose.yml` не перебиваются лежащим рядом `.env`. Пустое значение
в окружении тоже считается заданным. Если ключ повторён внутри самого `.env`, действует последняя строка.
Покрыто тестом `TestEnvPriority` в `tests/test_core.py`.

## Конфиг воронок (`funnels.yml`)

```yaml
settings:
  default_funnel: signup   # воронка без параметра /start
  stale_after: 5m          # опоздание, после которого шаг не отправляется
  send_pause: 0.1s         # пауза между отправками
  max_attempts: 3          # попыток при временных ошибках
  retry_delay: 5s

funnels:
  signup:                  # ключ воронки: t.me/<бот>?start=signup
    steps:                 # один список шагов. Сверху в ленте — неизменяемый «Триггер: /start»
      - key: has_phone     # ключ шага уникален в воронке; в очереди и статистике шаг опознаётся по нему
        kind: condition    # вид шага: message | delay | condition
        check: {kind: phone_given}   # проверка: phone_given («номер оставлен») или {kind: tag, tag: vip}
        on_true: already   # выходы указываются оба и явно: next (следующий по списку) | end | ключ шага
        on_false: next

      - key: welcome
        kind: message
        text: "Привет!"

      - key: ask_phone
        kind: message
        text: "Оставьте номер. Нажмите кнопку ниже."
        request_phone:               # шаг просит номер: кнопка запроса контакта и кнопка отказа
          button: "📱 Поделиться номером"
          decline_button: "Не хочу делиться"
        on_reply:                    # ветвление: куда идти после ответа человека
          contact: thanks            #   прислал контакт -> шаг thanks
          decline: declined          #   отказ (кнопка или любой текст) -> шаг declined

      - key: wait_1                # задержка — отдельный шаг: ничего не шлёт, потом следующий по списку
        kind: delay
        duration: 10s

      - key: reminder              # напоминание: уходит, пока ответа нет
        kind: message
        text: "Ждём номер — нажмите кнопку ниже."
        next: end                  # необязательно: явный следующий шаг (key | end)

      - key: already               # цели выходов и on_reply лежат в конце: по списку на них не «проваливаются»
        kind: message
        text: "Заявка уже у менеджера, ждите."
        next: end
      - key: thanks
        kind: message
        text: "Спасибо, заявка принята."
        next: end
      - key: declined
        kind: message
        text: "Хорошо, без номера."
        next: end
```

Полный рабочий пример — [`config/funnels.yml`](config/funnels.yml).

**Три вида шагов.**
- `message` — текст; может просить номер (`request_phone` + `on_reply`). Поля задержки у сообщения нет:
  перед ним ставится шаг `delay`. Старое поле `delay` у сообщения и раздел `entry_conditions` отвергаются
  с сообщением, что делать (конфиг прежнего формата нужно заменить на новый).
- `delay` — `duration`; отработав, ведёт на следующий шаг по списку. Своей цели нет. Это строка очереди со сроком
  «сейчас + длительность»; следующий шаг после неё получает срок паузы, поэтому правило о просроченном считается от расписания.
- `condition` — `check` и два выхода `on_true`/`on_false`, оба обязательны. Условие **ничего не отправляет и в очередь
  не встаёт**: бот вычисляет его сразу (событие `condition` в журнале) и идёт дальше, пока не упрётся в сообщение,
  задержку или конец. Проверки живут в `app/checks.py` (реестр `CHECKS`; имена сверяет тест с `config.CHECK_KINDS`),
  рядом с `phone_given` стоит `tag`. «Следующий по списку» у выхода условия — буквально сосед в ленте.

**Защита от бесконечных циклов.** При проверке конфига цикл, в котором нет ни одной задержки, отвергается
(он либо крутится вечно, либо заспамит человека); цикл с задержкой разрешён. На всякий случай и в бою: за один раз
бот проходит не больше `MAX_SILENT_STEPS = 20` условий без отправки (`app/plan.py`); упёрся — прогон закрывается
как `cancelled`, в журнал пишется `run_cancelled` с причиной.

**Как идёт воронка.**
- Планируется только следующий шаг, после отправки предыдущего; цепочка вперёд не расписывается.
  Следующий шаг — `next`, если он указан (`end` = конец), иначе сосед по списку, **если он не цель `on_reply`**;
  иначе прогон завершается. Поэтому напоминания идут одно за другим и кончаются, а «спасибо»/«отказ»
  по списку недостижимы и включаются только ответом.
- `request_phone` воронку **не останавливает**: запрос отправлен, напоминания идут по расписанию. Кнопка запроса
  живёт в чате и висит до замены, поэтому прикрепляется только на шаге запроса; в текстах напоминаний
  пишите «нажмите кнопку ниже».
- Ответ (контакт или отказ) отменяет ждущие шаги прогона, сохраняет номер и ставит метку и событие, после чего
  ставит шаг из `on_reply`. Ответа может не быть никогда: напоминания закончатся, прогон завершится по
  последнему шагу, срока ожидания нет. Контакт, пришедший уже после завершения, тоже обрабатывается
  (шаг «спасибо» уйдёт) — отвечать можно на последний запрос последнего не отменённого прогона.
- Шагов с `request_phone` в воронке может быть сколько угодно, ответ относится к последнему отправленному.
- Шаг, куда ведёт `on_reply`, заодно убирает клавиатуру запроса.
- Ветвление общее: `jump()` в `app/plan.py` «оборвать расписание и перейти на шаг». Контакт и отказ — два
  его применения; условия позже сядут на тот же механизм.

Проверки при разборе: цели `on_reply` и `next` существуют, `on_reply` есть только вместе с `request_phone`
и содержит оба ответа, `end` и `next` — не ключи шагов, у условия оба выхода на месте, в каждый шаг можно попасть,
цикл без задержки отвергается. Старые поля `welcome` и
`phone` отвергаются с понятным сообщением (иначе на устаревшем конфиге бот молча остался бы без приветствия).

Длительности: число секунд или `10s` / `1m` / `1h`. Можно описать несколько воронок.

Разбор — в одном модуле [`app/config.py`](app/config.py): `parse_config(dict)` проверяет структуру
(уникальность ключей, известные виды, ссылки между шагами, понятные сообщения об ошибках), `load_config(path)` читает YAML.
Новый вид шага = функция разбора в реестре `STEP_KINDS`. Страница-схема и редактор могут брать готовые
объекты `Config`/`Funnel`/`MessageStep` (`Funnel.next_step()` — единственное место, где определяется порядок) или проверять черновик через `parse_config`, не трогая обработчики.

## Редактор воронок

Мини-апп → воронка → «Редактировать» (кнопка только у администраторов из `ADMIN_IDS`). Лента шагов рисуется той же
`renderStep`, что и в просмотре; разница одна — шаг нажимается и открывает экран правки с полями под его вид
(текст, переключатель «Просит номер телефона», кнопки, выпадающие списки целей; у задержки — длительность; у условия — проверка и два выхода: следующий по списку / закончить прогон / шаг из выпадающего списка). Над лентой — неизменяемый блок «Триггер: /start» (в конфиг не попадает). «Добавить шаг» сначала спрашивает вид. Есть добавление,
удаление, «выше/ниже». Цели `on_reply` и `next` выбираются **из списка существующих шагов**, битую ссылку набрать нельзя.
Шаг, на который кто-то ведёт, удалить нельзя, пока ссылку не поменяют. Экраны переключаются в памяти страницы,
адрес и хеш с подписью Telegram не трогаются.

Запись идёт в тот же `funnels.yml` (`POST api/funnels/<ключ>`, путь относительный, как и остальные):
- **Комментарии и порядок ключей сохраняются:** файл читается и пишется `ruamel.yaml` (круговой разбор). Меняются только
  шаги выбранной воронки и только то, что реально изменилось; `10s` остаётся `10s`, если значение то же. Остальные воронки,
  `settings` и комментарии вне изменённых полей остаются как были.
- **Проверка перед записью — та же `parse_config`, что при чтении,** и не на черновике, а на перечитанном тексте, который
  собираются записать. Не прошло — файл не трогается, а страница показывает, что не так (нет текста/ключа, задержка не
  разбирается или отрицательная, `next`/`on_reply` на несуществующий шаг, дубли ключей, шаг, в который нельзя попасть
  от первого шага, и т. д.).
- **Запись безопасна:** временный файл в той же папке, затем `os.replace` одним движением; бот видит либо старый файл, либо новый.
  Поэтому в `compose.yml` монтируется папка `config/`, а не файл: подмена файла, смонтированного отдельно, даёт `EBUSY`.
  Папка должна быть доступна на запись пользователю процесса.
- **Права проверяет сервер:** без права редактирования запись получает `403`, файл не тронут. Скрытая кнопка — только удобство.
  Право: `ADMIN_IDS` или `DASHBOARD_AUTH_DISABLED=1` (локальный запуск; иначе в обычном браузере редактор не показать).
- **Бот подхватывает файл без перезапуска:** петля очереди раз в секунду делает один `stat` (inode, mtime, размер);
  изменился — перечитывает. Если файл правили руками и он сломан, бот остаётся на прежнем конфиге и пишет ошибку в журнал.

**Люди, идущие по воронке в момент правки.** Самое простое решение: правка действует сразу, идущие прогоны продолжаются
по новому конфигу (прогон хранит только ключ шага, не копию воронки). Если шаг, на который прогон должен был перейти
(ждущая запись очереди, цель `next` или `on_reply`), исчез, бот не падает: прогон закрывается как отменённый, ждущие
записи отменяются, в журнал пишется `run_cancelled` с причиной «шага '…' нет в конфиге» (виден в дашборде), а человек
при следующем `/start` начнёт воронку заново по новому конфигу. Если исчез шаг, на котором прогон ждал ответ, присланный
номер всё равно сохраняется и ставится метка, но дальше идти некуда — прогон закрывается так же. Отправка, уже взятая в
работу, доводится до конца по снимку конфига на момент взятия.

## Схема базы (SQLite, `data/bot.db`)

| Таблица | Поля |
| --- | --- |
| `users` | `tg_id` (PK), `name`, `username`, `phone`, `photo_file_id`, `created_at`, `tags` (JSON-список меток в самой записи) |
| `runs` | `id`, `user_id`, `funnel`, `status` (`active`/`cancelled`/`completed`), `started_at`, `finished_at`, `awaiting_step` (последний отправленный шаг-запрос без ответа), `jump_to` (ответ пришёл во время отправки шага). Частичный уникальный индекс: у пользователя не больше одного `active` |
| `queue` | `id`, `run_id` (обязателен), `user_id`, `funnel`, `step_key`, `due_at`, `status` (`pending`/`processing`/`sent`/`cancelled`/`expired`/`error`), `attempts`, `sent_at`, `error`. Частичный уникальный индекс `queue_one_open`: у прогона не больше одной записи в `pending`/`processing` |
| `events` | `id`, `ts`, `user_id`, `run_id`, `kind`, `details` — для списка событий в дашборде |

Время — unix-секунды. Метки: `phone`, `phone_declined`, `step:<воронка>:<шаг>`, `done:<воронка>`.
Метка `phone:<воронка>` ставится, когда человек прислал номер в этой воронке; условие на входе читает только её.
Метка `done:<воронка>` («прогон дошёл до конца») по-прежнему ставится, но условием не читается. Фото профиля: `file_id` сохраняется при первом `/start`,
картинка скачивается и кешируется в `data/photos/` только по запросу дашборда.

Уровни воронки в дашборде выводятся из журнала событий, а не из устройства воронки: **запустил бота** —
есть событие `run_started`; **получил запрос номера** — дошёл до шага с `request_phone`: событие `phone_requested`
пишется при отправке такого шага (даже внутри уже отменённого прогона: сообщение доставлено);
**дал телефон** — есть `phone_given`. Уровни вложены (номер можно дать только после запроса). Считаются по воронке:
событие привязано к прогону, прогон — к воронке. Воронка без запроса номера страницу не ломает: у неё второй и третий уровни равны нулю.

## Принятые решения (для разговора)

**Очередь в базе, а не в таймерах.** Шаг ставится записью «кому, что, когда». Петля раз в секунду забирает
подошедшее по сроку. Перезапуск процесса не теряет ожидающие записи и не дублирует отправленные: состояние
живёт в файле, а не в памяти. Планировщиков и `asyncio.sleep(60)` в обработчиках нет.
Забор — одним `UPDATE … WHERE id=(SELECT … LIMIT 1) RETURNING …`, который сразу ставит `processing`:
между «выбрал» и «пометил» нет щели для двойной отправки. Нужен SQLite ≥ 3.35 (в Python 3.12 и образе `python:3.12-slim` есть).
Если процесс упал в момент отправки, запись останется `processing`; при старте такие записи помечаются
ошибкой «прервано перезапуском, отправка не подтверждена» и **не** отправляются повторно: лучше потерять одно
сообщение, чем прислать дубль (подтвердить доставку после падения нельзя).

**Замок на файле (`flock`).** Два процесса на одной базе и одном токене дрались бы за `getUpdates` и могли бы
вдвоём рассылать очередь. `flock` снимает ядро, когда процесс умирает, даже от `kill -9`, поэтому «залипшего»
замка и ручной чистки нет. Замок берётся до импорта aiogram, так что второй запуск падает мгновенно и объясняет причину.

**Просроченное не отправляется.** После простоя в очереди могут лежать десятки записей. Если слать их все, бот
выпалит залпом сообщения, которые уже никому не нужны («через 10 секунд» пришло через сутки). Запись с опозданием
больше `stale_after` помечается `expired`; такой прогон остаётся `active` (не «пройден до конца»), и `/start`
запустит его заново. Правило действует и для шагов после ветвления (ответ → «спасибо», опоздавшее больше `stale_after`, не отправляется).

**Повторный `/start`.** Три случая, различаются строго, всё под замком на пользователя:
1. человек уже оставил номер в этой воронке (метка `phone:<воронка>`) — первый шаг поставляемой воронки, условие
   `has_phone`, ведёт на сообщение «заявка у менеджера» и конец. В чате это одно сообщение; в базе — короткий
   завершённый прогон (условие — шаг прогона, а сообщению нужен `run_id`). Условие «оставил номер», а не «дошёл до конца»: у кого напоминания кончились без ответа или кто отказался,
   номера нет, и на `/start` он начинает воронку заново. Условие по воронке: номер, оставленный в другой воронке, вход сюда не закрывает;
2. прогон идёт — он закрывается как `cancelled`, его `pending`-записи становятся `cancelled`, создаётся новый прогон
   (одна транзакция). Запись в `processing` отмена не трогает: отправка доводится до конца и честно записывается
   как `sent` внутри отменённого прогона — дашборд показывает это отдельной строкой;
3. впервые — обычный старт.
Два быстрых `/start` идут друг за другом (замок на пользователя, aiogram обрабатывает апдейты параллельно),
а индекс «один активный прогон» — страховка на уровне базы.

**Прогон завершается**, когда отправлен шаг, после которого цепочка кончается, и других записей у прогона нет.
Отменённый прогон завершённым не становится.

**Один неотправленный шаг на прогон.** Это держит индекс `queue_one_open`, а не только аккуратность кода.
Если ответ человека приходит, пока напоминание «в отправке», второй шаг не ставится: ответ запоминается в
`runs.jump_to`, напоминание доезжает (его отправка не отменяется), и целевой шаг ставится сразу после, а
следующее напоминание не планируется. Если напоминание в этот момент упало с временной ошибкой — оно заменяется
целевым шагом, а не повторяется.

**Сбои теперь обрывают цепочку.** Раз вперёд расписан только один шаг, просроченный (`expired`), упавший
навсегда (`error`) или потерянный при перезапуске шаг заканчивает цепочку: следующие не планируются, прогон остаётся
`active` без записей в очереди. Человек, ждущий ответ на запрос, всё равно может ответить; иначе помогает `/start`.

**Отказ от телефона.** Telegram не присылает событие «пользователь отказался», поэтому есть вторая кнопка
«Не хочу делиться», а отказом считается и любой текст вместо контакта. Клавиатура убирается, пишется событие
`phone_declined`, метка `phone_declined`, и ставится шаг из `on_reply.decline`. Чужой контакт (не свой) не принимается.

**Лимиты Telegram.** Отправка по одной с паузой `send_pause`. `RetryAfter` — ждём ровно `retry_after` секунд и
повторяем (попытка не засчитывается). «Бот заблокирован» и отказ запроса — ошибка без повторов. Сетевые и 5xx — до `max_attempts` раз.

**Доступ к дашборду.** Страница (`GET /`) отдаётся всем: это статичный HTML без данных, а подписанные `initData`
лежат в хеше ссылки (`#tgWebAppData=…`) и на сервер с этим запросом не приходят. Закрыт API (`/api/*`): страница берёт
`initData` из хеша (без внешнего скрипта `telegram-web-app.js`) и шлёт их в заголовке `X-Init-Data`. Сервер проверяет
HMAC-SHA256 с ключом от токена и свежесть `auth_date`. Любой, чья подпись настоящая, дашборд открывает; без Telegram
страница показывает «откройте из Telegram», данных нет.

**Кто видит телефоны и правит воронки.** `ADMIN_IDS` — не список доступа, а список тех, кому видно всё и кто может править воронки. Админам и при
`DASHBOARD_AUTH_DISABLED=1` телефон отдаётся целиком. Остальным с настоящей подписью — только последние четыре цифры,
остальное точками (`•••••••1222`); факт «дал телефон» виден всем. Замазывает сервер при сборке ответа
(`stats.mask_phone`): полный номер в JSON и в разметку не попадает вовсе. Замазывание в браузере не годится: номер
всё равно приехал бы в страницу, и его достали бы из DevTools. Если флаг «показывать целиком» где-то забыли
проставить, номера остаются замазанными (по умолчанию `reveal=False`). `DASHBOARD_AUTH_DISABLED=1` — только для
локального запуска; в журнал пишется предупреждение.
Фото отдаются через сервер (`/api/photo/<id>`), чтобы адрес файла с токеном не попал в страницу.

**SQLite без aiosqlite.** Запросы короткие, одно соединение в потоке event loop, WAL и `busy_timeout=5000`
включены явно; многошаговые изменения — в `BEGIN IMMEDIATE`. Лишних зависимостей нет: aiogram, aiohttp, PyYAML и `ruamel.yaml` (только для записи конфига с комментариями)
(дополнительно к ним pip тянет зависимости самого aiogram).

## Тесты

```bash
python3 -m unittest discover -s tests -v        # ядро, без внешних зависимостей
python3 tests/fake_telegram.py 8081               # заглушку можно поднять отдельно, TELEGRAM_API_BASE=http://127.0.0.1:8081
```

Сквозного прогона настоящего бота (aiogram на заглушке Telegram) в репозитории нет: в среде, где писался код,
aiogram и aiohttp не установить, значит, скрипт нельзя было прогнать, а непроверенный скрипт хуже отсутствующего.
Заглушка `tests/fake_telegram.py` осталась: `python3 tests/fake_telegram.py 8081`, потом бот с
`TELEGRAM_API_BASE=http://127.0.0.1:8081` и `BOT_TOKEN=любой` — ручная проверка связки. Ожидание `retry_after`
проверяется в `test_core.py` без гонок со временем (подменяемые часы и сон).

`tests/test_core.py` покрывает: повторный `/start` при идущем прогоне, после оставленного номера, после молчания и отказа, отмену только ждущих
записей, доведение до конца взятой в работу, просрочку, два быстрых `/start`, ожидание ровно `retry_after`,
отказ от телефона, подпись initData (нет подписи / чужой токен / подделана / устарела / отключено) и права (не-админ с подписью пускается,
но видит замазанный номер; админ и режим отключения — полный),
замок (второй процесс и `kill -9`), отсутствие токена и внешних ресурсов в странице.
`tests/test_editor.py` — редактор: каждая проверка конфига на своём неверном случае, запись через временный файл, отказ не-админу,
подхват нового файла без перезапуска, исчезнувший шаг/воронка/цель ветвления. `tests/test_yaml_roundtrip.py` — круг «чтение → запись → чтение»
с комментариями на настоящем ruamel.yaml (без него пропускается; в среде автора ruamel не было, см. отчёт).
`tests/test_dashboard_http.py` поднимает `preview_server.py` с включённой проверкой подписи и по HTTP проверяет:
без подписи API закрыт; не-админ с подписью — замазанный номер, полного нет ни в JSON, ни в разметке; админ — полный.
`tests/test_base_path.py` проверяет пути страницы: в `index.html` нет литералов с ведущей `/`; адреса `api/…` из страницы
разрешаются от адреса страницы и отвечают 200 и в корне, и под префиксом `/tg-demo/` (прокси срезает префикс, остальное
отдаёт 404); старые `/api/…` под префиксом получают 404 (негатив). `tests/prefix_proxy.py` — тот же прокси для ручной проверки.
`tests/test_api.py`: уровни по воронкам (в том числе воронка без запроса номера), список всех пользователей с маской,
структура шагов для страницы, статические свойства `index.html` (одна функция отрисовки шага, адрес не трогается).
`tests/preview_server.py` и `tests/build_preview.py` нужны, чтобы посмотреть вёрстку без бота.
